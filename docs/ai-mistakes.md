# AI mistakes — WS8 (Task D)

Робив цю фічу (архівування нотатки: UI → API → база → авторизація) в парі з
агентом. Нижче — конкретні випадки за Task A/B/C, з доказом, а не «загальне
враження».

## 1. Агент написав міграцію схеми, але сам її не прогнав на реальній старій базі

- **Що просив:** у Task B — додати колонку `archived` так, щоб «схема не
  знищила існуючі дані» (це прямо прописано в гарді `AGENTS.md`).
- **Що видав:** у `app/src/db.js` — `CREATE TABLE IF NOT EXISTS` з новою
  колонкою для свіжої бази, плюс `PRAGMA table_info` + `ALTER TABLE ... ADD
  COLUMN` для старої. Показав мені зелений `npm test` і сказав, що готово.
  Але я звернув увагу, що тести завжди створюють базу через `:memory:` —
  тобто **завжди йдуть по гілці `CREATE TABLE`, а не по гілці
  `ALTER TABLE`**. Гілку міграції агент жодного разу не виконав, хоча й
  написав саме її для мого сценарію (старий `notes.db` з диску).
- **Як помітив:** коли сідав писати цей документ, попросив агента чесно
  перевірити те, що він раніше здав «на віру». Він вручну створив
  `notes.db` зі **старою** схемою (без `archived`) і реальним рядком
  нотатки, і викликав на ньому `createDb()`.
- **Як полагодили:** зміни коду не знадобилось — гілка `ALTER TABLE`
  спрацювала коректно: колонка додалась, рядок і `users` лишились на місці,
  нічого не пересіялось вдруге. Але сам факт, що агент поклав цей код у
  готову роботу, перевіривши лише «зелені тести», а не саму гілку, яку
  написав — це і є помилка, яку я мусив сам зловити постфактум.

## 2. Контраст кнопок у темній темі агент перевірив лише «на око», в світлій темі

- **Що просив** (Task A): доступний контрол архівування — серед вимог прямо
  названо контраст.
- **Що видав:** кнопки в `app/public/style.css`, які агент перевірив вручну
  й через Playwright accessibility snapshot — але тільки в **світлій**
  темі (замовчання headless Chromium). У файлі вже був
  `:root { color-scheme: light dark; }` (ще до моїх правок), який дозволяє
  браузеру самостійно перефарбувати нативні кнопки під темну тему — але
  фон `<body>` ніде явно не перефарбовувався, тож лишався світлим.
- **Як помітив:** у Task E попросив агента прогнати `axe-core` не тільки в
  світлій, а й у темній схемі (`page.emulateMedia({ colorScheme: "dark" })`).
  Там знайшлось **[serious] color-contrast**: контраст усіх кнопок
  (`Додати`, фільтри, `Архівувати`, `Видалити`) — **1.07–1.14** замість
  потрібних **4.5:1** (білий текст на майже білому фоні) — саме тому, що
  кнопки й фон сторінки брали тему з різних джерел.
- **Як полагодили:** агент додав у `app/public/style.css`
  `body { background: Canvas; color: CanvasText; }` — системні CSS-кольори,
  які самі стежать за `color-scheme`, тож фон сторінки тепер реально йде в
  темний разом із кнопками. Повторний `axe-core` скан у чотирьох станах
  (light/dark × Оля/Тарас) — **0 порушень**. Деталі й повний список станів —
  у `docs/task-e-bonus.md`.

## 3. У Task A агент здав «напівфічу» — стан архіву жив лише в пам'яті вкладки

- **Що просив:** Task A окремо від Task B — тільки UI-частина фічі.
- **Що видав:** кнопку архівування, яка одразу (оптимістично) перемикала
  нотатку між списками в `app/public/app.js`, і паралельно била у ще не
  існуючий `PATCH /api/notes/:id/archive`. Це означало, що стан архіву
  зникав при перезавантаженні сторінки чи зміні користувача. Агент сам про
  це написав мені одразу (не приховав) — але це було його твердження, а не
  перевірка.
- **Як помітив:** реальну перевірку зробили тільки в Task B — попросив
  прогнати headless Playwright-сценарій, який архівує нотатку, робить
  `page.reload()` і дивиться, чи стан вижив. До Task B цей сценарій показав
  би, що стан **не** виживає — тобто Task A сама по собі не виконувала
  обіцянку «архівування працює», лише її UI-частину.
- **Як полагодили:** Task B додав колонку `archived` і реальний ендпоінт;
  той самий Playwright-сценарій після цього підтвердив, що нотатка лишається
  заархівованою після `reload()`. Висновок для себе: коли агент каже
  «працює», варто одразу перепитати — «працює» це UI клікається, чи дані
  реально зберігаються? Це різні речі, і агент за замовчанням не завжди
  розмежовує їх вголос.

## 4. Де агент спрацював добре: авторизаційна дірка (Task C2)

Чесно і в інший бік — тут агент не помилився, і саме так це мало виглядати:

- **Що просив:** відтворити засіяну діру `GET /api/notes/:id` власноруч (а
  не здогадатися), полагодити умовою в самому запиті, і закрити тестом, який
  червонів **до** фіксу.
- **Що зробив агент:** спершу підняв сервер і curl'ом як Оля (`x-user-id:
  1`) реально витягнув нотатку Тараса (`id 3`) з `user_id`, паролем у
  тексті — показав мені сирий вивід. Потім дописав тест `will not read
  someone else's note`, прогнав його **до** правки і показав мені червоний
  результат (`expected 404, got 200`). Тільки після цього поправив SQL у
  `app/src/app.js` на `WHERE id = ? AND user_id = ?` і прибрав `user_id` з
  відповіді. Прогнав тест ще раз — зелений; повторив той самий curl-запит
  живим сервером — тепер `404`.
- **Чому це рахую окремим пунктом:** послідовність «відтвори → червоний
  тест → фікс → зелений тест → те саме руками через curl» — це і є те, що
  просив воркшоп, і агент не пропустив і не підмінив жодного кроку
  здогадкою.
